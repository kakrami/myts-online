# Projection control-witness throughput repair

## Scope and reproduced cause

The deployed 7.2.13 fair-service change made source analytics and tracking jobs run. Match analysis correctly remains deferred while its own season has an unpublished structural projection. Live read-only diagnostics then identified a distinct event-page bottleneck: a stable 110-event season advanced with an adaptive event page size of one. The exact filtered matcher control set contained 100 relevant jobs, with 71,789 UTF-8 bytes for the existing 17-field job representation, including 22,763 bytes of serialized arguments and 3,196 bytes of checkpoints. These aggregate observations contain no private provider payloads or player records.

The existing projector copied all relevant schedule jobs into every inferred-game receipt. Its 15,000-byte admission threshold reduced a requested event page from 24 through smaller sizes to one even though this team-wide portion did not shrink with the event page. A singleton still saved conservative native output, so this was slow progress rather than a stalled SQL transaction. The page-size reduction did not itself prove a SQL-budget failure.

Synthetic measurements reproduced the exact three live byte aggregates with generated data. Ordinary productive pages perform 23 reads and five staged writes whether they contain one or several events; paired-neighbor pages perform 24 reads and ten writes. Those figures exclude installation/coordinator overhead and are not hosted latency predictions. A jobs digest/count reference reduces the measured 24-event receipt to 5,804 bytes for ordinary sources and 6,874 bytes for the mixed-source case, while the complete raw job evidence remains about 79,687 serialized parameter bytes for exact transactional comparison.

## Safety boundary

The repair must preserve complete source coverage and matching decisions. A stored digest alone is not sufficient: each relevant page and publication must reacquire complete scoped control evidence, compare its identity, and fence the same exact raw evidence inside the committing transaction. Relevant subscriber edges are part of that evidence because removing one root's edge from a shared job can change coverage without changing the union of job IDs.

Existing valid version-one receipts and published pointers remain supported. Interrupted building runs need an explicit migration rule: a previously staged conservative native row must not be combined with a newly inferred group across the old cursor. Any incompatible hidden run must rebuild safely without removing the last published pointer or owner state.

The schema, scheduler fairness, source collectors, authority gates, 16 KB persisted proof limit, 8 KiB checkpoint limit, 2 MB transaction limit and 50-statement invocation limit are not throughput knobs.

## Implementation boundary

Version-two receipts reference a SHA-256/count witness of complete ordered job, coverage and subscriber sets. The full raw controls remain transient. The frame acquisition reads the distinct control-validation inputs, rather than repeatedly copying each owner-qualified receipt's source universe and windows. That avoids a new total-season cliff from otherwise identical control evidence. Committing SQL seals the exact projected input set and the same freshly acquired raw controls, including cardinality. Each full publication still receives its source, canonical identity, owner-state, expiry and strict non-control shape checks.

Valid version-one controls remain supported. A changed control digest, raw argument/checkpoint string, relevant subscriber edge, added/deleted job or coverage change must fail the read-to-commit check. Full stored-fence hash-only changes with unchanged validated semantics are not claimed as rejected; that is metadata rather than the new control witness.

A policy marker permits a saved small event page to be reassessed once at its existing cursor. When new verified grouping conflicts with a previously staged conservative native row, the hidden run is obsoleted and rebuilt through the existing identity phase. The previous published pointer is retained. This is an intentional migration cost, not a reset of saved source data or owner state.

## Frozen verification receipts

The frozen 7.2.13 native baseline reproduced the exact source-scale byte totals under the full 788-statement installation and epoch wrapper. Five event invocations reduced 24 to 12, 6, 3 and 1, then saved one conservative native row. The productive invocation used 45 of 50 SQL statements, returned 181,841 instrumented result bytes, and had no inferred accepted group despite independently complete and eligible pair evidence. Its before/after source map was identical: `e3ac5ef331fd03a6d1e979b4e68df9c45ad035fe432aef81abd55cb9ebc20169`.

The candidate used the same generated 100-job control set and 110 source observations (100 TeamSnap events and ten genuine GotSport peers). It published 100 logical games, 110 current-pointer native members and all ten accepted mixed-source pairs. The event phase used five productive pages of 14, 24, 24, 24 and 14 games, followed by one empty phase-transition page. The complete main projection used 17 coordinator invocations. The mixed first page used 44 physical/count SQL statements; the four remaining productive pages used 39 each. Stored page size stayed 24.

Across all six event-phase invocations, instrumentation counted 215 physical SQL statements, 675,689 SQL bytes, 908,793 bound-parameter bytes and 1,674,566 returned-result bytes. Native D1 metadata reported 182,289 rows read and 979 rows written. Those are aggregate physical costs, not per-statement limits. The maximum individual SQL statement was 32,455 bytes, the largest per-statement parameter payload was 105,065 bytes, and the largest transaction contained 16 statements, 56,506 SQL bytes and 320,616 parameter bytes. The maximum checkpoint was 256 bytes and the maximum stored fence was 4,637 bytes. The unchanged 50-statement, 2 MB transaction, 8 KiB checkpoint and 16 KB stored-proof limits were respected.

Eight held data-bearing coordinator pages rejected atomically: raw argument whitespace, raw checkpoint whitespace, coverage-scan change, subscriber-generation change, added job, deleted job, owner correction and root revocation. The subscriber-only case retained all 100 exact job rows, so its rejection specifically proves the additional edge binding. Each case used at most 44 statements. Successful projection preserved native/canonical identities and the existing owner venue correction. Foreign-key checks passed and the installation permit was closed. Native D1 does not provide rows-read/written metadata for the rolled-back failing transaction; negative metrics cover successful acquisition and claim only.

The migration test actually invoked the frozen 7.2.13 collector against the same preserved native database. It staged the public half of a verified pair as a native-only size-one row, leaving its private peer beyond the cursor. The candidate's first resumed invocation obsoleted that incompatible hidden run while preserving the last published pointer. A replacement run went through the existing identity phase and atomically published 100 games, 110 pointer-selected members and ten pairs. Raw historical table totals include prior/obsolete runs and are not the user-visible counts.

One actual match-analysis job settled against the initial newly published pointer and its exact source clock, before the migration scenario. Its result was explicitly unsupported, with zero players, because this fixture has no Trace payload. This proves pointer-bound admission and settlement; it is not a new useful-Trace-analytics or analyzed-count receipt.

The candidate native test passed 1/1 on exact frozen runtime commit `1ccc99d1af33cf7d3f9fc5ceb107b04c81c86e6a`. Its 185-file before/after source maps were identical, with fingerprint `e088fb2d2e69b7f6ed10187b6653a07ccb08b4ad41ae0d2d7be17afe382295cd`. Both full baseline and candidate maps are retained in `projection-control-native-map.json`. Regenerating the release manifest changes that generated map entry only; all executed runtime bytes remain identical. The native fixture is a one-season throughput, held-race and migration proof. New two-season control-witness assertions are covered by the SQLite/coordinator and native-D1 SQL-shape compilation tests, not a newly repeated two-season native workflow.

The integrated pure regression command passed 290/290 with zero skips or failures in 226.215 seconds: candidate loading, projection, two-season publication and compact controls. The independent reviewer passed the focused 41/41 compact-control cases on identical runtime bytes. The writer also passed 159 overlapping pre-existing projection/candidate/two-season cases, and two SQL-shape tests with maximum 48 and 49 coordinator statements. These overlapping runs are separate receipts, not additive unique test counts.

Both baseline and candidate native tests used host-driven production coordinator/collector calls against Workerd native D1, the full 788-statement installation and production epoch writes, respecting real 500 ms continuation waits. They did not test production alarm delivery. The baseline deliberately stopped after page collapse and one productive row, so no full-baseline elapsed-time ratio is asserted. Candidate total native duration also includes held failures, analysis and migration; it is not a hosted throughput prediction. All observations and test identities are synthetic. No production reset or manual checkpoint mutation is required.

## Release and remaining acceptance

Version 7.2.14 changes only the five projection/control-witness runtime paths and the visible version. Schema 788, installation fingerprint/plan, scheduler, collectors, dependencies and authority policy remain unchanged. The required-only archive contains the runtime dependency closure and retained evidence documents; tests, local logs, native receipts, private live QA files and dependency directories are excluded.

Live acceptance still requires normal deployment, safe continuation or hidden-run rebuild from the existing cursor, current-pointer membership publication, and real Trace analysis from available data. The measured improvement removes repeated oversized receipt work; it does not guarantee universal per-job latency or claim full product acceptance.
