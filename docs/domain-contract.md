# myTS fresh-build domain and API contract

Status: design proposal for review; no production changes in this document.

The original frontend is the behavior and appearance baseline. This contract changes how data is collected, linked, queried, and authorized. It does not authorize replacing its screens, reports, filters, editors, or Coach interactions. The first implementation must prove one complete team workflow before the remaining features are connected.

## 1. Observed defects and their shared cause

The following boundaries were inspected in the current 7.0.1 source:

| Current code | Finding | Required boundary |
|---|---|---|
| `src/providers/teamsnap.js`, catalog branch | Discovery writes `spaces` and `space_teams` using the native TeamSnap ID and imports every discovered team. | Discovery writes provider records and account entitlements. A domain action creates or attaches an app team. |
| `src/api.js`, spaces POST | Manual creation uses unrelated UUIDs. There is no shared attach flow for TeamSnap. | Team creation has one provider-independent identity and explicit attachments. |
| `src/routes/catalog.js`, players | A correction adds `trace_player_id` but both provider player rows remain in the returned roster. | All roster views query canonical players and source memberships. |
| `src/api-helpers.js`, fixturePage | One manual non-Trace-to-Trace link suppresses a duplicate. Other provider pairs remain separate. | All event views query one canonical event model with generic source links. |
| `src/routes/catalog.js`, competitions/status | Competition filtering and paged job rows do not provide a complete team read contract. | Filters precede paging. Summary totals and revisions cover the full authorized selection. |
| `src/jobs.js` | Provider-native fixture IDs and account-independent private job IDs are mixed with app identities. TeamSnap has a special scheduling predicate outside subscriptions. | Private source/job scope includes its account entitlement. All work has explicit demand. |
| `src/routes/connections.js` | Team unlink and account disconnect have different, incompletely exposed effects. | Distinct account-wide and team-only lifecycle commands. |
| `src/auth.js` | `ADMIN_KEY` signs sessions and determines provider credential encryption. | Independent authentication, session, and credential-key lifecycles. |
| `src/services/analytics.js` | Corrections are selected through generic kinds, overloaded season strings, and provider player IDs. | Typed corrections address canonical match, half, player, and season identities. |

The existing job lease, transaction fence, bounded provider transport, saved checkpoints, and periodic server wakeup remain useful mechanisms. They need the correct source and domain scopes. Keeping a mechanism does not preserve an old database or a compatibility reader.

## 2. Domain invariants

1. An app team ID is generated by myTS and never derived from a provider ID. Changing providers, accounts, names, or seasons cannot change that ID.
2. Provider discovery cannot create visible app teams, alter owner team names, or attach sources implicitly. Explicit onboarding can perform a selected create-and-attach action in one transaction.
3. A selected source team can attach to an existing app team and season regardless of which provider was connected first. Repeating the same attachment is idempotent.
4. Each linked person has one canonical player ID within this installation and one roster entry per selected team-season. A player can have distinct jersey, role, and active membership in different seasons or teams.
5. A source member/profile is not assumed to identify the same person across unrelated accounts. Name, jersey, or approximate age alone cannot merge people.
6. Each confirmed corresponding source event maps to one canonical event. Team participation is a relation, so one event can involve two managed teams without copying its shared facts.
7. Team-specific logistics, attendance, private analysis, and Coach data remain team-scoped even when the event's public schedule identity is shared.
8. Public competition/team/division/match records are collected once per provider resource and reused through subscriptions. Private source records are scoped to the account entitlement that retrieved them.
9. Owner corrections do not rewrite source records. A successful refresh updates source evidence and preserves corrections.
10. The same effective projection supplies screen details, totals, reports, exports, and Coach inputs. A correction has one interpretation everywhere.
11. A source omitted from one incomplete page is not a deletion. Membership removal is reconciled only after a complete, validated scan.
12. Final scores are not frozen forever. A provider can correct an official result. Conflicting evidence is preserved and surfaced; the owner can choose a value or leave it unresolved.
13. A canonical entity's source links cannot cross a forbidden private scope. Every write validates team membership, source visibility, entity type, and revision.
14. User-visible status distinguishes collection coverage, execution state, analysis readiness, and data freshness. A finished fetch is not proof that match reconciliation or analysis is complete.
15. A failed, blocked, or disconnected source does not prevent independent sources from updating. Saved data and its freshness remain visible until an explicit removal action changes that scope.

## 3. Fresh schema responsibilities

Names below define responsibilities, not a mandate for arbitrary extra tables. Final SQL must use foreign keys, explicit uniqueness, checks, and indexed query paths. There is one fresh installation schema and no upgrade code.

This is the existing single-owner application with TeamSnap, GotSport/Live, and Trace. Do not add organizations, tenants, role hierarchies, a plugin framework, a universal entity store, or a general workflow engine. Public sharing retains the application's existing read-only scope. Account scoping prevents wrong-account imports and private data leaks within this installation; it is not a new multi-user product.

### App identity and team context

| Relation | Essential key and purpose |
|---|---|
| `app_teams` | `id`; owner-managed team name, selected club, timezone, revision, creation time. Names are not unique identity keys. |
| `team_seasons` | `id`, `app_team_id`; original season label and June 1–May 31 schedule boundaries, June inclusion preference for statistics, revision. Unique `(app_team_id, start_date)` prevents accidental duplicate rows. |
| `players` | `id`; stable person identity and owner display defaults. No provider/native ID columns. |
| `roster_memberships` | `(team_season_id, player_id)`; jersey, role, participation state, source memberships. |
| `events` | `id`; stable game/practice/other identity and domain revision. Shared match identity is separate from any provider event ID. |
| `team_events` | `(app_team_id, event_id)`; team-season assignment, participation side, typed effective date/time/type/status/scores, selected source references, projection input revision. This indexed read model supplies lists and totals. |
| `event_participants` | `(event_id, side)`; own app-team ID or source-team reference, with a label fallback for unresolved opponents. |

A source team's season label is evidence, not the application's season definition. Preserve the original `seasonYearForDate` (`month >= 6`) and `scheduleDaysForSeason`: June 1 through May 31, represented as `[June 1, next June 1)` in queries. The original `includeJune` setting controls statistical inclusion of June/preseason games; it does not move the visible calendar season to July–June. The 7.0.1 July–June rule is a regression. The TeamSnap team for last year can attach to a different season of the same app team. A Trace profile that spans seasons can have date-scoped attachments. A provider team need not be copied per season. Do not add a new customizable season-policy interface.

### Provider accounts, source data, and entitlements

| Relation | Essential key and purpose |
|---|---|
| `provider_accounts` | `id`, unique `(provider, native_account_id)`; display identity, authorization state, encrypted credential reference, authorization generation. |
| `account_source_teams` | `(account_id, source_team_id)`; discovered access and last complete discovery scan. Authentication does not attach all rows. |
| `source_clubs`, `source_teams` | Provider-native club/team identities with typed names, club relation, season label, archive flag, visibility scope, observation time, and bounded evidence. |
| `source_players`, `source_roster_memberships` | Provider-native player identities and source-team membership with typed names/jerseys/active state/scan ID. No JSON roster lookup. |
| `source_events`, `source_event_teams` | Provider-native event identity and participating source teams; typed kickoff or local day, time precision, type, status, participants, competition/division, and scores. |
| `source_competitions`, `source_divisions`, `source_competition_memberships`, `source_standings` | Shared public competition facts with typed dates/names/registration/pool/team/rank/points/statistic columns needed by existing queries. |
| `source_attendance` | Source event/member IDs, native response code, normalized yes/no/maybe/unanswered state, observation time. Preserve unavailable versus no response. |
| `team_source_attachments` | `id`, `app_team_id`, optional `team_season_id`, source team, optional account, active state, generation. Uniqueness makes reattachment idempotent. |
| `event_source_links` | A source event maps to one event in its authorized scope; verified link reason, evidence, and revision. |
| `player_source_links` | A source player maps to one player in its authorized scope; verified link reason, evidence, and revision. |
| `matching_candidates` | Entity kind, source pair/canonical target, evidence, state, rejected reason, revision. A rejected candidate does not reappear unchanged on every refresh. |

Public GotSport/Live records are reusable across managed teams and bookmarks. TeamSnap/Trace source payloads, availability, personal identifiers, cookies, tokens, and private notes are never treated as public merely because a public match has been linked to them. Shared links authorize a team projection, not arbitrary database source IDs.

### Minimal typed SQL choices

Use concrete relational tables, not `source_objects`/`source_relations`. Searchable and aggregatable facts are columns. Native evidence is bounded ancillary JSON and never the central query model. Source IDs are internal opaque keys; uniqueness is `(provider, scope, native_id)` on source identity tables. `scope='public'` requires `account_id IS NULL`; a private scope requires `scope=account_id` and an account foreign key. TeamSnap and private Trace rows cannot use the public scope.

Minimum column choices for the first vertical slice:

- `source_teams(id, provider, scope, account_id, native_id, name, club_id, season_label, archived, observed_at, content_hash, evidence)`.
- `source_players(id, provider, scope, account_id, native_id, name, jersey, observed_at, content_hash, evidence)`.
- `source_roster_memberships(source_team_id, source_player_id, active, scan_id, observed_at)`; composite primary key and index by player.
- `source_events(id, provider, scope, account_id, native_id, source_competition_id, source_division_id, starts_at, local_day, time_precision, type, status, home_source_team_id, away_source_team_id, home_label, away_label, home_score, away_score, observed_at, content_hash, evidence)`.
- `source_event_teams(source_team_id, source_event_id, side)`; composite primary key and index by event. TeamSnap opponent labels need not invent source-team identities.
- `source_attendance(source_event_id, source_player_id, native_status, response, observed_at)`; composite primary key and response check.
- `team_source_attachments(id, app_team_id, team_season_id, source_team_id, account_id, active, generation)`; explicit uniqueness uses a non-null season scope or a checked all-seasons scope, not nullable columns that defeat SQLite uniqueness.
- `event_source_links(source_event_id, event_id, reason, evidence, revision)` and `player_source_links(source_player_id, player_id, reason, evidence, revision)`; source ID is unique and foreign-keyed.
- `team_events(app_team_id, event_id, team_season_id, own_side, starts_at, local_day, type, status, goals_for, goals_against, schedule_source_id, result_source_id, input_revision, revision)`; indexes cover team/season/time, team/status, and event.
- `team_read_state(app_team_id, content_revision, status_revision)`; two monotonic counters are enough. Account discovery uses its account/catalog revision.

The existing competition/Trace/Coach tables can be reshaped to these responsibilities when those workflows are connected; do not create empty platform tables for hypothetical future integrations. Source competition table keys remain provider-native shared records. Match/player statistics use typed per-match/player/period facts where the original tables and reports aggregate them. Heatmaps/tracking retain bounded per-match/team/player/half/chunk evidence rather than thousands of SQL inserts for individual coordinates.

Persist only unresolved/rejected matching decisions needed to avoid repeated prompts. Separate player and event candidates can use concrete foreign keys; a polymorphic generic relationship graph is unnecessary. Store the current derived analysis with an algorithm version/input revision rather than retaining every historic algorithm output.

Large Trace data stays in bounded match/team/player/period/chunk records. An installation, team, season, or full-account JSON snapshot is not an allowed primary storage structure. Source response bounds remain deliberate limits; a legitimate oversized dataset must be paged or segmented without losing the surrounding workflow.

### Corrections, analysis, and interface-owned records

| Relation | Essential key and purpose |
|---|---|
| `overrides` | Team scope, target type/ID, optional match/half/season scope, field or typed correction group, value, revision, timestamp. Match IDs and season IDs have separate columns. |
| `match_analysis` | `(event_id, app_team_id)`; current algorithm version, input revision/hash, observed/estimated/manual evidence, coverage, warnings, derived results. Bounded player/half detail can be separate child records. |
| `coach_profiles`, `coach_sessions` | Canonical team/season/player/event IDs, CAS revision; never exposed to read-only shared viewers. |
| `favorites` | Team scope plus canonical event or public source-team reference. |
| `branding` | Team/club/season scope and revision; shared source logo plus explicit owner override. |
| `shares` | Hashed opaque token, team scope, existing read-only sharing contract, revoked state. No new permissions editor. |
| `team_read_state` | Team ID and monotonic content/status revisions covering the entire visible context. |

Identity linking is a domain relationship, not a cosmetic correction field consumed by only one endpoint. Source-to-source mapping of Trace tracking IDs is distinct from the TeamSnap-to-Trace person link. Dummy tracers and unresolved opponent tracks are not canonical roster players.

## 4. Field ownership and effective projection

The resolver returns values with provenance: source references, observed time, effective rule, and conflict or confidence state. It does not silently combine disagreeing final scores or add the same goal/minute twice.

| Field group | Normal authority | Override behavior |
|---|---|---|
| Team display name, chosen season, kits | Owner selection; provider values prefill creation | Owner value persists independently of source names. Reset exposes the current source/default choice. |
| Roster identity, attendance response | Linked TeamSnap member and availability when connected | Canonical identity/attendance corrections are explicit and team/match-scoped. Unknown responses remain unknown. |
| Official competition/division, bracket, standings, official result | Verified GotSport/Live competition relationship | Manual choice can resolve a conflict for myTS; it does not overwrite public provider evidence. |
| Private arrival time, uniform, availability settings, team notes | TeamSnap event | Only present for the permitted team context. A public viewer projection uses the declared sharing policy. |
| Kickoff, venue, cancellation/postponement | Explicit team schedule policy; official competition event for official fixture facts, TeamSnap logistics kept separately | Disagreements retain source evidence and a visible conflict. A rescheduled event keeps its canonical identity. |
| Video, clips, heatmaps, tracking and raw performance | Trace event/team records | Manual match/person corrections modify the effective analysis with provenance. Source data remains inspectable. |
| Lineup and position | Manual match/half correction, then usable heatmap inference, then manual season default | Missing heatmap data cannot erase a manual lineup or prevent a season default from applying. |
| Scorer/assister and minute correction | Manual match/player correction over available source evidence | One correction feeds match detail, player totals, season totals, reports, and exports. |

The existing original-app behavior determines any provider precedence that is still unspecified. This table makes conflicting facts an explicit decision instead of disguising them with `COALESCE`, provider order, or a permanent "FINAL never changes" exception.

Minutes preserve the agreed 7v7/9v9 rules, separate field and goalkeeper time, exclude dummy/opponent tracks, and show inference. For a 9v9 50-minute full-strength match the normal total is 450 player-minutes. Verified dismissals or intentionally short-handed intervals can reduce capacity. Estimates cannot be presented as measured minutes. Allocation, limits, match corrections, and reset behavior need the same tested function across every output.

## 5. Matching and ambiguity

Automatic linking requires verified provider relationships or sufficiently specific corroborating evidence with no conflicting candidate. A GotSport native external key in a verified Live relationship is useful evidence. Similar team names, equal scores, and kickoff proximity are candidates rather than identity proof.

Player candidates can use a confirmed team-season, normalized name, and supporting source metadata. Equal jersey alone never proves a link. Event candidates use participating identities, event type, competition/registration when available, date/time precision, and independent supporting details. Doubleheaders, tournaments, pending kickoff times, cancelled replacements, and swapped home/away ordering must remain distinguishable.

For unresolved candidates, preserve separately identified entries and show the existing matching/editor affordance with the supporting evidence. Do not hide one uncertain event or player to make counts look complete. Confirming a link yields one projected entry immediately; unlinking recomputes the projection without deleting source facts. Link/unlink uses compare-and-swap and rejects many-to-one collisions unless the domain action is an explicit merge with checked consequences.

## 6. Concrete first workflow

1. Owner initializes a genuinely empty database and signs in using the familiar application setup.
2. Owner connects a provider account. Account authentication and team discovery are separate states. The original TeamSnap one-time Client ID entry stays inside the login flow, not general Settings or a new deployment requirement. Preserve the original implicit authorization flow and `/admin` callback; changing it to `/oauth` would require a registered redirect change and is not an architectural improvement. Do not invent a password grant or other authorization path.
3. The discovery chooser lists real team names and seasons. Owner creates the app team from one selection or attaches the source to an existing app team. GotSport accepts supported search/public links; numeric IDs are advanced input.
4. The attachment creates subscriptions and wakes server jobs. A read-only page never needs to call the manual job runner to maintain freshness.
5. Source imports save bounded rows and checkpoints. Domain reconciliation creates/links canonical events and players; ambiguous records remain visible for resolution.
6. Owner attaches the second provider to the same app team. No second app team is created. The schedule, roster, detail tabs, and totals share the same identities.
7. Owner corrects a linked player/scorer/lineup through the existing editor. All views and exports use the correction.
8. Every browser is closed. Actual scheduled jobs retrieve a changed provider value, commit it, update projections/analysis, and advance the team revision.
9. Owner reopens the app. The provider value is fresh, the correction is retained, no duplicates appear, and success/status timestamps reflect the actual checkpoints.
10. Owner unlinks one source team, reconnects its account, then reattaches. Unlinking affects that attachment only; account disconnect clearly affects all attachments of that account. Existing canonical team identity and selected saved-data policy are preserved until explicit deletion.

## 7. Read/query API contract

Routes should fit the audited original frontend. The following are resource contracts; they do not require adopting these exact URL spellings or changing navigation. Original frontend calls can be updated to these resources without a second legacy API or old-schema reader.

Preserving a UI contract means preserving user-observable behavior and accepted outputs. It does not require carrying the original monolithic worker's private function names, snapshot-shaped payloads, or duplicate calculation code into the fresh backend. Implement one frontend data-access layer that maps new canonical read resources to the original screen models. Move pagination-sensitive totals and shared statistics into the backend and bind the existing table/editor components to those results. This adapter is current frontend code, not a legacy database/API compatibility layer. Retain DOM structure and interactions unless a demonstrated workflow defect requires a small explained change.

| Resource | Contract |
|---|---|
| Bootstrap | Owner-visible app teams, selected context, preferences, version, authentication state. Provider credentials/configuration are owner-only and returned only when needed. |
| Account discovery | Works before a team exists. Account identity, authorization state, discovered teams/seasons, discovery progress, next required action. |
| Create/attach | Explicit source selection, existing/new team decision, season selection, idempotency key; returns one canonical team ID. |
| Overview | Complete filtered season aggregates, latest result, next event, standings, performance leaders, coverage, and team revision. Preserve original included-game/season choices. Never computed from one list page. |
| Schedule | Canonical events, Day/Season and All/Games/Practices/Analyzed filters, local-date boundaries, complete visible calendar range, stable sort/cursor, coverage. |
| Competitions | Season and own/all-team filters applied before pagination; matches and standings refer to shared public data with source freshness. |
| Roster/statistics | Canonical players and full-selection aggregates; server search/sort and complete totals; active/season membership is explicit. Preserve the original Team statistics, Roster, and Trophies views, not only a list of names. |
| Match/player detail | The original detail tabs' data, attendance, heatmaps, H2H, source evidence, corrections, matching state, and required previous/next IDs within the same selection. |
| Sync status | Complete summary and team status revision plus optionally paged job details. Account-required actions remain owner-only; shared viewers receive safe freshness/coverage. |
| Reports/export | Original Season Summary, Schedule, Players, and Attendance report workflows; exact filter/sort/season scope, complete dataset, stable revision, same projection and analysis as screens; no export of only the current page. |
| Lifecycle | Separate rename/remove team, attach/unlink source, reconnect/disconnect account, revoke share, and reset correction commands with defined scope and CAS. |

Every collection applies authorization, identity resolution, season/date/type filters, and selected corrections before aggregation and pagination. Responses include `selection`, `items`, `next_cursor`, `total`, `coverage`, and `revision` where relevant. A date-only event stays a date-only event; it is not converted to invented midnight kickoff. UI "today", past/upcoming, calendar boundaries, and season queries use the same team timezone. Carry the original June inclusion choice in the statistical selection; calendar and game discovery still cover the full June–May season.

Keyset cursors encode the validated selection/sort and a stable dataset revision. For ordinary changing lists the server can return an explicit restart requirement after a revision change. Reports require a fixed projection snapshot: materialize the selected rows once, or read from versioned rows. Do not promise snapshot consistency while simply paging mutable live rows. Bounded export jobs can create XLSX/PDF from that snapshot when the selection is too large for one request.

`team_read_state` advances transactionally when source projections, identity links, corrections, settings, favorites, branding, or analysis affect the team. `status_revision` also changes for errors, blocked authentication, retry timing, and job transitions. An account discovery revision updates the chooser even when the currently selected team already exists. Polling reads these complete revisions, not signatures of the first 40 jobs. Polling frequency is a presentation concern, never the background scheduler.

## 8. Jobs, demand, and recovery

Keep the persisted lease token, lease expiry, connection generation fence, atomic page commit, repeated-pagination detection, bounded observations, independent task kinds, retry delay, Durable Object alarm, and Cron fallback. Remove the TeamSnap-only "primary team" scheduling exception in favor of a uniform demand model.

Job identity is `(provider, authorization_scope, kind, source_resource_key)`. Public scope is shared. Private scope includes the provider account; job IDs for account A cannot be silently reassigned to account B on reconnect. Job arguments hold resource keys and bounded options, not a duplicate credential or full team snapshot.

Account discovery is account-demanded. Team imports are attachment-demanded. Public bookmarks/competitions are subscription-demanded. Child jobs inherit the relevant demand references. Removing the final demand pauses/cancels its jobs; public data can remain reusable. Unlinking while a public job runs must prevent writes to removed team projections even if other consumers still need the public record.

Execution states: `queued`, `running`, `retry_wait`, `blocked_auth`, `blocked_verification`, `paused`, `idle`. Coverage is separate: `uncollected`, `partial`, `complete`, `unsupported`. Analysis readiness is a separate dependency/input-revision result. Record last attempt, successful retrieval, successful commit, complete scan, next scheduled check, and safe error details.

Authentication failures stop blind retry loops until account renewal. Verification blocks cannot be solved by fabricated success or repeatedly hammering the same endpoint. Transient failures back off with provider retry hints. Source-contract errors preserve evidence for diagnostics. Expired leases resume from the last committed cursor; stale generations cannot commit source rows, derived rows, or child jobs. Scheduler recovery is verified under crash, unavailable provider, exhausted invocation budget, and changed account generation.

A reconciliation/projection task carries the source input revision and commits only against that revision. Source collection can finish while downstream analysis is pending; status must show both. Schedule/roster availability need not wait for Trace analytics. Fair job selection avoids one large historical import starving live schedule/results updates. Refresh intervals are explicit per resource; manual retry requests only make eligible work due.

### Source commit and domain commit boundary

1. A collector returns typed provider rows, bounded evidence, the next cursor, scan completion, and source-task requests. It never returns `app_teams`, canonical players/events, owner overrides, or visible team attachments.
2. The source commit transaction checks the job lease/account generation, upserts changed typed source rows, records the checkpoint, and atomically marks affected attachment projections pending. Record hashes prevent unchanged pages from needlessly rebuilding every roster/statistic. Public fan-out is bounded and resumable; do not issue one SQL operation per follower.
3. A projection task reads one bounded affected team/event/roster slice and its input generation. It assigns/links canonical identities, applies typed owner corrections, writes effective `team_events`/roster/analysis inputs, and advances the team's content revision in one guarded transaction.
4. A stale projection cannot publish against a changed attachment/account/source input. Retrying the same slice is idempotent. The source checkpoint can be complete while projection remains pending; the status contract exposes that distinction.
5. Owner linking/unlinking/correction commands use the same domain resolver and guarded write rules. They do not modify raw provider rows or leave list/detail/report projections disagreeing until a page reload.

Small source/domain slices may be committed together when the transaction remains bounded; that is an optimization, not a second reconciliation implementation. Larger imports use the persisted pending projection task. Never claim atomicity across separately committed source and domain transactions.

The current wrapper permits 48 statements per invocation. Reserve the complete transaction cost before fetching or constructing a commit, including lease checks, observation writes, checkpoint, pending projection demand, and final status/revision updates. A rollback-safe transaction must fit the remaining budget. Page writes should use set-based upserts with bounded JSON parameters into typed tables, not one query per record. Projection fan-out, roster matching, and analysis must page by stable keys and save checkpoints; they cannot each scan the whole account on every source page. Read APIs use indexed canonical projections and SQL aggregates rather than reading every source row and running reconciliation during a GET request. Measure statements and D1 rows read/written for the first complete workflow, including retries and unchanged scheduled refreshes.

## 9. Security and sharing lifecycle

Use independent secrets for initial owner authentication, session signing, and provider credential encryption. Ordinary owner password changes revoke sessions as appropriate without invalidating stored provider credentials. Encryption stores a key identifier; a deliberate encryption-key rotation is a separate operation with verified decrypt/re-encrypt behavior, not a side effect of password change. This is within the fresh build's operational lifecycle and does not introduce an old-version migration.

Provider credentials reside once per account in server storage. Team attachments refer to the account. Reauthentication increments an account generation and invalidates stale fetch commits. Auth pending requests have opaque owner/session-bound identifiers, expiry, rate limits, and one-time use; concurrent attempts cannot overwrite one global `trace` pending record.

Authorization is enforced before database reads, not by hiding UI tabs. A share token grants one team projection and declared categories. It cannot enumerate accounts, roster data from another team, unlinked private source data, raw auth errors/secrets, or Coach records. Linking a public event to a private Trace event does not make the private event's payload public. Account configuration such as OAuth application identifiers is kept in the authorized connection flow and is not leaked through every viewer bootstrap.

## 11. Validation cases and acceptance evidence

### Identity and provider order

- Fresh installation starts without any app-owned tables; initializing twice has defined safe behavior; binding a populated incompatible database refuses rather than upgrades it.
- Connect TeamSnap first, GotSport first, Trace first, and create manually first; explicit attachments produce one selected app team in every order.
- Discover ten provider teams; only selected teams become visible app teams. Archived native teams can attach to historical seasons of the same app team.
- Repeat attach/create submission and reconnect with a timeout; no duplicate team, source link, or demanded job appears.
- Link two source players; all roster/detail/statistics/Coach inputs refer to one canonical player. Another same-name player remains separate.
- Link one match across TeamSnap/GotSport/Live/Trace; schedule, counts, attendance, video, H2H, reports, and bookmarks represent it once.
- Doubleheaders, unknown kickoff, home/away swaps, rescheduled events, and equally plausible players produce reviewable candidates, not silent merges.
- Unlink identity and reset correction; source records remain intact and projections update consistently.

### Ownership, corrections, and data completeness

- A source refresh changes names, time, result, and roster; manual values survive and reset exposes the new source values.
- A provider corrects a final score; evidence is retained, conflict handling does not permanently freeze the old score, and effective totals follow the accepted result.
- Match/half/manual lineup takes precedence even with no heatmap. Heatmap inference and season fallback follow the declared order.
- Known scorer mismatch, goalkeeper plus field time, dummy tracers, opponent tracks, and corrected person IDs yield consistent player and team statistics.
