# Projection control evidence lifetime

## Observed failure and reproduced cause

The 7.2.14 release removed the oversized per-page proof bottleneck, but live projections still rebuilt before publication. Read-only deployment evidence confirmed that the active Durable Object was executing the reviewed release. Previously staged hidden runs contained 24 and 32 event rows, so missing policy markers observed after a reset did not establish a stale Worker or failure to execute the new page path.

Those hidden runs became obsolete while the season's structural input remained unchanged. The previous accepted publication stayed readable. The exact live control row that changed was not captured, so the following causal reproduction is deliberately distinguished from attribution to a particular provider job.

On the exact deployed source tree, a synthetic SQLite fixture staged an accepted game publication. Changing only an already-complete GotSport history job's scan and save/completion timestamps made the next projection invocation obsolete the hidden run. Repeating this sequence produced the same reset three times with identical source rows and season input. A second case used the production JobCoordinator claim and successful complete commit rather than directly changing those fields; it produced the same reset with unchanged job generation and arguments.

The version-two receipt persisted an exact digest of all 17 job fields for the lifetime of a multi-page build. Ordinary recurring work changes several of those fields even when saved source evidence is unchanged. Exact execution metadata is necessary to seal each individual transaction, but it is not by itself a change to previously established game identity or accepted completeness evidence.

## Required boundary

The repair separates previously validated accepted evidence from the exact current control values used for each transaction. It must retain structural job and subscriber identity, source scope, provider account and authorization generation, accepted completeness meaning, the captured source neighborhood, and all existing native-source, root, owner and publication checks. Every committing transaction must still compare the complete freshly read raw job, coverage and subscriber sets, including cardinality.

A completion timestamp alone is not proof of complete evidence: the coordinator may finish a partial or unsupported response, and a new claim can clear an old checkpoint. A new page may therefore reuse only an applicable, explicitly validated accepted proof or wait for genuine complete evidence. Such a wait must retain its hidden run and cursor, have a bounded durable due time, and create neither a failure loop nor a rapid empty-page loop.

Old receipt versions keep their original interpretation. Any necessary hidden-run migration must retain the current published pointer and owner state. Routine refresh or a later fetch failure must not manufacture first-success evidence, erase native observations, or claim current provider freshness.

## Implemented lifetime and waiting rules

Version-three receipts use a version-two semantic control witness. It retains exact job identity, provider/account scope, authorization and job generation, component, stage, native scope/resource, serialized arguments, subscriber edges and stored coverage meaning. Scan IDs, execution state/checkpoint and observation/completion timestamps are still compared exactly by the fresh transaction assertion; they no longer invalidate an already-proven multi-page lifetime by themselves.

An accepted-evidence marker is created only after the existing typed coverage validation succeeds. It distinguishes complete collection across the source scope from a TeamSnap neighborhood proven only because it lies outside an active recent-refresh window. Only the former can authorize a later neighborhood in the same hidden run, and only for explicit connection roots with unchanged scope and structural frame. New neighborhoods are still acquired, resolved and fenced from their current exact source rows. Legacy attachments and outside-active-window evidence do not acquire this broader authority.

A small checkpoint proof also retains authentic full-scope evidence when the first page contains only native games and therefore creates no game-association publication. It is committed under the same exact raw-control comparison, bound to its run, and remains below the existing checkpoint cap. A fresh run cannot borrow this authority from an old published pointer or reinterpret an old raw witness after its controls change.

Without applicable prior proof, currently active source collection causes a typed 60-second deferral. The queued job retains its run and cursor and automatically becomes due again. Terminal failed or unsupported evidence follows the existing conservative behavior. The coordinator accepts this deferral only for an unfinished domain projection; other collectors cannot request it. Execution-only or unrelated global-clock changes detected during acquisition similarly retain the cursor, while structural scope changes retain the existing invalidation behavior.

The schema, source collectors, scheduler class rotation, authority gates and hard limits are unchanged. The scheduling delta is limited to that validated projection continuation delay.

## Verification

The frozen 7.2.14 native baseline passed its causal-defect oracle. The full 788-statement installation and epoch wrapper first published 100 logical games, 110 current-pointer source members and ten accepted pairs from the generated 100-job control set. A replacement run at unchanged structural input staged its first 24-ID page, which contained 14 logical rows after pairing. An actual recurring history claim, production empty-response collector and coordinator commit then changed scan/checkpoint/save metadata without changing the captured source, participant, canonical-link or root hashes. The next projection invocation obsoleted that hidden run and preserved the accepted pointer.

That bounded native baseline used a maximum of 44 SQL statements per invocation, a 348,471-byte collector transaction payload, a 259-byte checkpoint and a 4,637-byte stored fence. Native D1 reported 259,262 rows read and 1,547 rows written across the fixture. The source maps were identical before and after, with fingerprint `669228ff89e118882ce24a0f90d309fba7db22e394d7f3fb5bf9b828e41ec035`. The fixture uses host-driven production calls and real continuation waits, rather than production alarm delivery. It establishes a failure mechanism, not the exact live job that caused a reset or a hosted latency estimate.

The frozen candidate's known SQLite-only regression set passed 247/247 with zero skips or failures. This includes old exact receipt interpretation, repeated refreshes, native-only first-page proof, TeamSnap window boundaries, typed deferral and scope/transaction negatives. Measured SQLite compilation used at most 48 coordinator statements for ordinary projection and 49 for the two-season path. A 100-control, 24-game acquisition/staging case used 24 reads, ten writes, an 835,402-byte transaction payload and a 938-byte checkpoint. These measurements exclude native installation overhead, which is checked separately.

An earlier mixed aggregate accidentally included existing Miniflare test files and was stopped with exit 130. That interrupted run is retained as an incomplete attempt and is not counted as a pass. The subsequent 247-case selection was explicitly SQLite-only.

The first candidate native attempt stopped when the harness received no claim after a continuation deadline. Its receipt did not capture enough state to establish the exact cause. The harness now waits until the actual saved deadline is strictly past and records eligibility state if the claim is still absent; it does not alter production gates or deadlines. That incomplete attempt is not a pass.

A subsequent candidate run completed recurring-refresh publication and the real deferred continuation, then exposed a first-scan classification gap. Fourteen conservative native rows were staged, with zero accepted pairs and ten version-two pending receipts, so no accepted completeness was invented. The required active initial dependency should nevertheless have deferred. A nine-line loader correction now waits only when the exact, uniquely bound active component can supply the missing coverage; unrelated active jobs cannot hide terminal or unsupported evidence. Its focused paired tests passed 19/19, and the reviewer independently passed five relevant boundary cases. The incomplete native receipt remains retained separately.

The final native candidate passed on exact runtime commit `7b05dff5665cfb0e0291c23d1cc601b102716e05`, version 7.2.15. It exercised 149 production invocations and 26 actual synthetic-provider refreshes in 203.1 seconds, including the real continuation waits. One catalog job stayed continuously running while history refreshes completed between projection pages. The same hidden run published 100 logical events, 110 current-pointer native members and all ten verified pairs. Pair acceptance increased from three on the first page to five, seven, nine and ten on later pages, proving new-neighborhood acceptance during the active refresh rather than only retaining already-staged pairs.

The candidate fixture deliberately interleaves nine synthetic canonical pairs across later pages. The baseline keeps its original canonical ordering. Both retain the same 100-job/71,789-byte control shape and 100/110/10 final totals; no elapsed-time comparison between those differently ordered scenarios is asserted.

Both the new-run active-start and the first-ever incomplete-proof case retained the accepted pointer, waited without a failure, and resumed automatically after actual source completion and their saved 60-second deadlines. The latter did not use a fixture reconciliation write to force continuation. All twelve held transaction negatives rejected atomically. Relevant source, membership, owner, account, root, scope, job-set and subscriber changes remained guarded; raw checkpoint/coverage freshness also remained exact at the committing-transaction boundary. A real frozen version-two receipt scenario safely rebuilt its hidden run and published the same totals under overlapping refreshes.

The native maximum was 44 counted and actual SQL statements per invocation, a 345,958-byte collector payload, 312,086 transaction parameter bytes, a 947-byte checkpoint and a 5,499-byte stored fence. Across measured production calls, D1 reported 2,631,816 rows read, 7,786 rows written and 3,354 statements. Foreign-key checks passed and the installation write permit was closed. These totals include multiple success, rejection, continuation and migration scenarios; they are not a per-season hosted cost or latency promise.

The 185-entry executed source map was identical before and after, fingerprint `84a0f8064db62613e18ff2e253696d888efcdea9db6202e75907c643d10d80ee`. The harness decoded files as UTF-8 before hashing: 184 text entries match raw bytes, while the unused binary font requires the explicitly recorded exception. Its actual bytes match exact baseline and final Git with SHA-256 `ae7b7855e115a5966d8b1b3f80f254ccc117ec86f9965e202ee2940453837280`. Both executed maps and that exception are retained in `projection-control-lifetime-native-map.json`. The test-only helper is corrected for future raw-byte maps. Regenerating the release manifest changes that generated entry only; no executed runtime bytes changed after native verification.

The required regression includes actual recurring collector/coordinator work between projection pages at the observed 100-job scale, exact transaction-race negatives, first-ever incomplete coverage, TeamSnap full/recent receipts, preserved legacy publication, durable deferred continuation, and publication before the recurring workload is drained. The existing 50-statement, 2 MB transaction, 8 KiB checkpoint and 16 KB stored-proof limits remain unchanged.

## Release and remaining acceptance

Version 7.2.15 changes six runtime files plus the displayed/package version. Schema 788, installation fingerprint/plan, dependency versions and deployment bindings are unchanged. No production checkpoint reset, source data mutation or owner-state migration is required. An old strict witness may cause one ordinary hidden-run rebuild while the previously published pointer stays available.

The required-only archive includes the runtime closure and evidence documents. Tests, native logs/receipts, local build outputs, dependency directories and private live QA files are excluded. All new fixtures are synthetic. A clean extracted release check and dry-run bundle are part of final packaging verification.

Live acceptance still requires an actual stable replacement publication and useful Trace analysis from the already collected data. The native fixture establishes projection liveness and authority under repeated refresh; it does not claim production alarm delivery, hosted latency, real Trace quantities or full-product completion.
