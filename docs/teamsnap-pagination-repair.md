# TeamSnap collection repair — 7.2.1

## Confirmed live failure and release boundary

On 2026-10-12 the deployed 7.2.0 TeamSnap events and attendance jobs failed permanently with `record_too_large`, before saving any page or row. Both provider endpoints returned HTTP 200. The recorded 2,002,944 bytes are where streaming crossed the unchanged 2,000,000-byte response limit, not the total collection size. Roster, locations and opponents succeeded. The connected account and logical team remain valid; reconnecting or recreating them is not the recovery.

This patch changes code and visible version only. It retains the 731-statement schema fingerprint `e1c1b6cf96cd12afce94dc14819e103283aacac2f420329cfaf65938888e4f40` and upgrade plan `755a9a58c834e2a469c8d12e91acd9e51e67800efc7cb4c5e315e037c7170cc7`. The already completed 7.2.0 installation does not run another schema transition. Keep both databases, current owner/vault/provider credentials, connection and job identities, ADMIN_KEY, SYNC, cron, preview setting and 30,000 ms CPU limit. No import, reset, schema SQL or account reconnection is part of deployment.

## Bounded collection and convergence

- Events and attendance request explicit provider pages of 25 items. Exact endpoint, team, filters, page size and monotonically increasing page number are validated. Duplicate query keys, changed scope and ambiguous continuation fail visibly.
- If a requested page itself exceeds the existing response limit, its persisted size reduces through 25, 12, 6, 3 and 1. Collection restarts at page one, preserving saved observations. A single oversized item fails explicitly; neither caps nor source records are silently widened/truncated.
- Each provider page is divided into byte-budgeted database prefixes. The cursor advances only for rows in the same fenced commit. The estimator leaves room for checkpoint, audit and bounded generated projection children under the existing 2 MB coordinator parameter limit and SQL limits.
- Completion requires two consecutive complete observed traversals with matching ordered normalized-row digests, page counts and totals. Locally generated observation timestamps are excluded. Changes within a partially saved page restart that page. Changes across traversals retain saved rows and restart comparison.
- Each traversal rejects adjacent native-ID overlap and repeated native-ID sets among its last eight completed pages, independent of row ordering. This bounded guard catches the reproduced server repeating one page while claiming a larger total. It is not a global ID registry or a provider snapshot guarantee. Synthetic acceptance compares every expected native identity with the saved database.
- No 200-page history cutoff applies. Checkpoints retain bounded counters, digests and the recent-page guard. Three unstable traversals or three repeatedly changing local slices pause for 15 minutes with visible `source_changing` recovery rather than spinning forever or claiming completion.
- After one complete full-history traversal is saved, its verification phase yields to existing connection reconciliation and projection jobs through a scoped effective scheduling priority. Persisted priorities, authority, SQL budgets, aging and ordinary recent-window scheduling remain unchanged. Saved first-pass events are eligible for ordinary connection reconciliation and publication before verification completes. Coverage stays partial until verified. Terminal source coverage counts the entire accepted traversal, not only its last database slice; job observation counts may include verification reads.

The API exposes no verified snapshot token. Two matching observations and repeat checks are convergence evidence, not proof that a concurrently changing server was atomically snapshotted. Absent records are not deleted merely because a traversal omitted them.

## Refresh cadence and truthful status

Initial collection, Update now on a completed scan, and a full scan eligible after 24 hours traverse all history. Retrying an interrupted current-format scan resumes its saved full or recent window; the deployed failed legacy checkpoints restart full under the new protocol. Normal recurring events and attendance scans use documented event-date bounds from 30 days before to 90 days after the scan start. That window is fixed across retries/resume. Older edits and far-future events await the next eligible full scan and its successful completion. A scheduled full check is not a promise of completion within exactly 24 hours when the provider fails or keeps changing.

A typed, account/generation/argument-bound completion receipt survives ordinary ready-job claims. It stores full-history and recent-window receipts separately. Recent coverage cannot overwrite the last verified full-history count or timestamp, authorize replacement, or imply full collection. Manual refresh of a completed scan, changed arguments or changed authorization restart a full scan. Status shows the last full-history check, last finished scan and exact recent window.

`updated_since` exists in historical official TeamSnap metadata, but its timestamp syntax and completeness semantics were not verified. This release does not depend on it.

## Separate catalog repair

The live catalog failure followed `/me` and `/teams/search` success with a request to bare `/teams`, then `unsupported_response`. Official fixtures identify bare `/teams` as a metadata/queries resource that may omit `items`. This supports a possible explanation; the actual private response body was not available, so the precise live catalog cause remains unproven.

Bare `/teams` links now normalize to the existing verified account-scoped team search and deduplicate it. Archived/filtered team searches remain intact. Missing items is accepted only for an error-free search response whose own-account endpoint and full query exactly match the requested search. Metadata, malformed responses, duplicate keys and foreign account/filter responses fail closed. This is not a global missing-items-to-empty conversion.
